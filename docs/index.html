Your Verizon Family account, from the command line.

safe_cli is an unofficial command-line tool for the Verizon Family account you administer. The everyday controls are subcommands (pause-internet, filter, apps, website); every other operation the app performs is reachable through call. It is built to be driven by an agent or a script: --json output, a self-describing surface, and --dry-run for every request.

What it controls

The controls from the app, as subcommands.

Each area is a command with typed flags. Ids you would otherwise have to look up (profile, device, a category's fields) are resolved for you from the child's service id.

// pause-internet

Pause the internet

pause for 30m, 1h, 2h, 4h or until morning, or --indefinite; --call-only keeps phone calls working. resume lifts it (a repeat is a no-op, not an error). status shows the current state.

// filter

Content filter

show lists the filter with each subcategory's id and whether it is blocked; block and allow flip one by id; set --preset applies an age group (none, young-child, child, teen); categories and presets list the rest.

// apps

Apps

list shows the apps the filter knows, grouped (Messaging, Social Media, Games, …), with ids; --find narrows by name. block and allow act on one app.

// website

Websites and safe search

block and allow add domains to the block list or the trusted list, list shows both with the entry ids remove takes, and safe-search enable|disable enforces safe search on the child's search engines.

Everything else: call <entity> <op> Location and place alerts, screen time and bedtime, contacts and call restrictions, driving, service and subscription details, device pairing. entities lists the areas, describe lists an area's operations with what each needs.
How it works

One grammar: safe_cli <area> <verb> --child <SERVICE-ID>

A read prints a table, or JSON with --json. A write refuses an unpaired device unless you pass --allow-unpaired, and anything destructive refuses without --confirm. --dry-run prints the exact request, ids resolved, without sending it.

$ safe_cli areafilter verbblock who--child 1000002 what--category 10003
blocking a content category 
$ safe_cli filter show --child 1000002 --find drugs     # which id is it?
{ "categories": [ { "id": "OBJ", "name": "Objectionable", "subCategories": [
      { "id": 10003, "name": "Drugs, alcohol, gambling", "enabled": false } ] } ] }
$ safe_cli filter block --child 1000002 --category 10003 --dry-run
# target: Kid  (service 1000002, profile 2000002, device 3000002, PAIRED)
POST /parental-control/frisco/v8/subcategory HTTP/1.1
x-fp-identifier-target-serviceid: 1000002

{"subcategory":{"categoryId":1001,"categoryShortName":"OBJ","enabled":true,"id":10003,"name":"Drugs, alcohol, gambling"}}
# The category's fields were filled in from the filter. Drop --dry-run to send.
$
Get started

Build it, log in with your own Verizon account.

You sign in through the normal Verizon login in your browser; safe_cli never sees your password. The login needs the app's request-signing key, which you read from your own copy of the app (auth extract-key); the key is not part of the project.

1

Build

git clone https://github.com/ejc3/safe_cli && make build (Go, no CGO).

2

Log in

safe_cli auth login walks the device OTP, the Verizon login and 2FA. Tokens are stored locally and refreshed on their own.

3

Find your family

safe_cli members lists everyone with the service ids you pass as --child.

4

Make a change

Run a verb with --dry-run first, then without. --help on any verb lists its flags and prerequisites.

Scope and safety

Your account only.

What this is for

Administering your own Verizon Family account, in the same spirit as the community tools for Google Family Link, Microsoft Family Safety and Nintendo parental controls. It is unofficial: not affiliated with, endorsed by, or supported by Verizon or Smith Micro, and it can break when the service changes. You are responsible for using it only on accounts you administer.

Nothing of yours is in the project

No passwords, tokens, app files or family details are committed: not in the code, the tests or the docs. Tokens live in a mode-0600 file on your machine. The request-signing key is never written to disk or logged. Emergency features (SOS, rescue, roadside) are never triggered by tests.
